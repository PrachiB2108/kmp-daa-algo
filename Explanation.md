# Project Explanation: KMP vs. Boyer–Moore

This document is a simple guide for presenting the mini project. You can use it
as a speaking outline and as a checklist for running the demonstration.

## 1. Project in one sentence

This project takes a piece of text and a smaller pattern, then shows how two
algorithms—Knuth–Morris–Pratt (KMP) and Boyer–Moore—find every place where the
pattern occurs.

**Example**

- Text: `ABABDABACDABABCABAB`
- Pattern: `ABABCABAB`
- Result: the pattern starts at index `10` (counting from zero).

## 2. Why this project is useful

Searching for a word or sequence is a common computer task. A simple search
might compare the pattern at every possible position, repeating many character
checks. KMP and Boyer–Moore use information from earlier comparisons to avoid
some of this repeated work. This project makes their search steps visible and
measures how their work changes with different text types and sizes.

## 3. The two algorithms in simple terms

### KMP (Knuth–Morris–Pratt)

KMP reads the text from left to right. Before searching, it builds an **LPS
array** for the pattern. LPS means “longest proper prefix that is also a
suffix.” A prefix is the beginning of a string; a suffix is its ending. “Proper”
means it is shorter than the whole string.

If a mismatch happens after some characters matched, KMP uses the LPS array to
keep the part of the pattern that could still match. It does not need to start
over from the beginning of the pattern. The search phase takes $O(n)$ time,
where $n$ is the number of text characters; building the LPS array takes
$O(m)$, where $m$ is the pattern length.

**Easy way to explain it:** “KMP remembers how much of the pattern can still
match after a mismatch, so it does not recheck text characters unnecessarily.”

### Boyer–Moore

Boyer–Moore lines the pattern up with the text and compares from the **right
end** of the pattern toward the left. When it finds a mismatch, it uses two
rules to decide how far to move the pattern:

- **Bad-character rule:** use the text character that caused the mismatch and
  the character's last position in the pattern to choose a shift.
- **Good-suffix rule:** use the part of the pattern that matched just before
  the mismatch to find a safe shift.

It chooses a safe shift based on the rules and often skips several text
positions at once. With larger alphabets, a mismatching character is less
likely to appear in the pattern, so the bad-character rule can often skip
farther.

**Easy way to explain it:** “Boyer–Moore starts comparing at the pattern's
right end. When it finds a mismatch, it uses what it learned to jump forward
instead of checking every alignment.”

The code uses the bad-character and strong good-suffix rules. It does not
include the Galil optimization; therefore, do not claim that this particular
implementation guarantees linear worst-case matching time. Its typical
performance is often very good, but the theoretical general worst case can be
$O(nm)$.

## 4. What the website demonstrates

The website is a static page made from HTML, CSS, and JavaScript. It runs both
JavaScript algorithm implementations in the browser, side by side.

- **Text and Pattern:** edit the input boxes or choose a preset.
- **Play / Pause:** animate the comparisons.
- **Step / Step Back:** move through the recorded comparisons individually.
- **Run to end:** show the final result without watching the animation.
- **Speed:** change the animation delay.
- **Green highlight:** the compared characters match.
- **Red highlight:** the compared characters do not match.
- **Purple outline:** a character is part of a found occurrence.
- **LPS array:** KMP's precomputed fallback information.
- **Good-suffix shift table:** Boyer–Moore's precomputed shift information.
- **Benchmark section:** charts generated by the Python benchmark program.

The website works without a backend or database. GitHub Pages can host it as a
static site.

## 5. How to run the website for a demo

### Recommended: run it from VS Code

1. Open the repository folder `kmp-daa-algo` in VS Code.
2. Open a terminal with **Terminal → New Terminal**.
3. Check that the terminal is in the repository root (the folder containing
   `index.html`).
4. Run:

   ```powershell
   python -m http.server 8000
   ```

5. Open <http://localhost:8000> in a browser.
6. Keep the terminal open while presenting. To stop the local server, return
   to the terminal and press Ctrl+C.

You can also open `index.html` directly in a browser. The local server method
is recommended because it behaves more like the deployed website.

### Suggested live demo

1. Select **Classic** and point out the text and pattern.
2. Click **Step** a few times. Explain that the green and red cells show the
   algorithm's current character comparison.
3. Point out that KMP and Boyer–Moore can make different numbers of comparisons
   because they use different rules after a mismatch.
4. Open the KMP LPS table and explain that it tells KMP how much of the pattern
   it can keep after a mismatch.
5. Open the Boyer–Moore good-suffix table and explain that it helps choose a
   safe shift after a suffix matched.
6. Click **Run to end** and show the match position and number of comparisons.
7. Choose **DNA** and then **English prose**. Explain that DNA has only four
   possible letters, while English text has a larger alphabet and spaces; this
   can affect how far Boyer–Moore can skip.
8. Scroll to the benchmark charts and describe the comparison-count trend.

## 6. How to run the Python code

The Python folder contains a separate reference implementation for tests,
command-line demonstration, and benchmark generation. The website itself does
not need Python once it is hosted.

From the repository root, open PowerShell and run:

```powershell
cd python
python -m pip install -r requirements.txt
python -m unittest tests.test_algorithms -v
python demo.py
python benchmark.py
```

What each command does:

- `python -m pip install -r requirements.txt` installs Matplotlib, which is
  used to make benchmark charts.
- `python -m unittest tests.test_algorithms -v` checks the Python algorithms
  against Python's built-in string search, including overlapping matches and
  edge cases.
- `python demo.py` runs a small example and prints matches, comparison counts,
  and times.
- `python benchmark.py` runs the experiments and creates CSV and chart files
  inside `python/results/`.

The charts currently shown on the website are committed in `benchmark-data/`.
Running the Python benchmark creates a fresh local `python/results/` folder;
it does not automatically update the website's committed chart files.

## 7. What the benchmark measures

The benchmark records three things for each algorithm:

1. **Preprocessing comparisons:** character comparisons made while building
   KMP's LPS array or Boyer–Moore's good-suffix table.
2. **Matching comparisons:** character comparisons made while searching the
   text.
3. **Elapsed time:** time spent on preprocessing and matching, measured in
   microseconds by Python's timer.

The benchmark uses five seeded runs for each data point and averages them. It
uses a 12-character pattern for the standard text-length and alphabet-size
experiments. Patterns are selected from the generated text, so a match is
present in those benchmark inputs.

The test inputs include:

- **DNA-like text:** random characters from `A`, `C`, `G`, and `T` (alphabet
  size 4).
- **English-like text:** random characters selected using approximate English
  letter frequencies, including spaces. This is generated pseudo-English, not
  a passage from a book or a natural-language corpus.
- **Uniform synthetic text:** random characters over alphabet sizes 2, 4, 8,
  16, 26, 32, 64, and 94.
- **Binary pattern comparison:** a randomly selected pattern and a
  repeated-prefix pattern shaped like `aaa...ab`.

A note about the last experiment: the repeated-prefix pattern is an
illustrative test input, not a guaranteed worst-case input for Boyer–Moore.
The benchmark does not prove the theoretical worst case. Runtime values also
vary between computers and runs, so comparison counts are usually more useful
for explaining the algorithmic trend.

## 8. Main observations

From the committed benchmark run with a 100,000-character text and a
12-character pattern:

- For DNA, KMP made about 124,140 matching comparisons. Boyer–Moore made
  about 32,855.
- For English-like text, KMP made about 107,516 matching comparisons.
  Boyer–Moore made about 12,443.
- Boyer–Moore made fewer matching comparisons in these measured cases. Its
  shift rules were more effective for the larger-alphabet English-like input.
- KMP's search remains $O(n)$ regardless of the alphabet, because its fallback
  rule controls how the pattern moves.

These are results from the project's particular generated inputs and settings,
not a promise that Boyer–Moore will always be faster. For a very short text or
pattern, preprocessing and implementation overhead can matter more.

## 9. Complexity symbols

- $n$: number of characters in the text.
- $m$: number of characters in the pattern.

| Algorithm | Preprocessing | General worst-case search |
|---|---:|---:|
| KMP | $O(m)$ | $O(n)$ |
| Boyer–Moore in this project | $O(m)$ | $O(nm)$ |

Boyer–Moore often inspects fewer than $n$ text characters on typical inputs,
but this implementation does not use the Galil optimization required for a
linear worst-case guarantee in common variants. This distinction is useful to
mention if asked why the title or benchmark says the algorithms are fast while
their worst-case bounds differ.

> “My project compares KMP and Boyer–Moore, two algorithms for finding a
> pattern inside a text. KMP preprocesses the pattern into an LPS array and
> uses it to avoid restarting after a mismatch. Boyer–Moore compares from the
> right side of the pattern and uses bad-character and good-suffix rules to
> skip ahead. The website animates the comparisons, and the Python program
> tests both algorithms and measures comparisons and time on DNA-like,
